# Subscription route metering boundary

Read-only inspection on September 24 used the installed `marketing-hire:dev` image (`openclaw@2026.9.4`) and the matching local OpenClaw source checkout (`package.json` version `2026.9.4`). The source checkout contains unrelated edits; none were changed. No model request, auth change, or fallback activation was made for this inspection.

## What the installed runtime supports

- The existing `openai/gpt-5.6-luna` subscription route currently selects the native Codex app-server harness for the Marketing worker. Its completed turn reports aggregate usage, while Codex owns native network retries. The host cannot stop the 21st provider request or reserve its tokens from that turn-level reply.
- Version-matched `docs/concepts/agent-runtimes.md` and `docs/providers/openai/runtimes.md` in the OpenClaw checkout describe an explicit provider/model `agentRuntime.id: "openclaw"` route that retains a selected `openai` OAuth profile through OpenClaw's internal Codex-auth transport. Runtime policy can be scoped to the worker via `agents.entries.*.models["provider/model"]`; it need not switch the owner's direct Chat.
- The OpenClaw plugin reference classifies `before_agent_run` as a gate **before a turn**. It classifies `model_call_started`, `model_call_ended`, `llm_input`, and `llm_output` as observations. Those hooks do not provide a documented, fail-closed admission decision before **each underlying provider request**. A provider `wrapStreamFn` extension exists, but a stream invocation is not evidence that internal transport retries are individually admitted.
- The version-matched OpenClaw source builds `openai` SDK clients with `maxRetries: 0` for built-in text transports, and `buildGuardedModelFetch` is the deeper transport fetch function. That function is not currently exposed as a per-request admission plugin hook. `createOpenAIResponsesClient` accepts an internal `fetchOverride`, but the exported `createOpenAIResponsesTransportStreamFn()` takes no arguments, so the ordinary provider `wrapStreamFn` hook cannot inject this override. The Responses transport also has its own replay, continuation, and compaction paths; a stream-wrapper count alone remains insufficient proof of network-request coverage.
- Source trace: `packages/ai/src/transports/openai-responses-client.ts` calls `createResponsesStreamWithEncryptedContentRetry` for one stream. `packages/ai/src/transports/openai-responses-replay-internal.ts` loops around `client.responses.create(...).withResponse()` after rejected encrypted reasoning, compaction, or continuation state, and can retry after a streamed rejection. Each loop iteration may send another HTTP request while one stream wrapper remains active. The installed native Codex harness adds its own opaque network behavior. A turn or stream hook cannot honestly write a complete provider-request ledger.

## Staged request ledger

The hire SQLite ledger has `model-reserve` and `model-finish` commands. Each reservation binds an execution ID, network request ID, exact request-body digest, and a caller-supplied token allowance. One SQLite transaction refuses a 21st pilot request, a request exceeding the 250,000-token pilot total, or one exceeding the 25,000-token current execution reservation. A repeated request ID never grants another send. Missing usage, reported overrun, and restart during a reserved request hold further admission. A top-level result cannot settle while one of its model requests is unresolved, and a confirmed per-request total cannot be undercharged by a smaller aggregate turn report. Synthetic negative controls pass, and the new schema loaded against the preserved live project without changing its status or usage. The historical pilot has no per-request receipts, so its underlying provider count remains unknown.

The boot source pins only `runway-worker` to `agentRuntime.id: "openclaw"` for `openai/gpt-5.6-luna`; the owner's main Chat route and empty fallback list are unchanged. A disposable config copy with that one override passed `openclaw config validate --json` on installed `2026.9.4` with no warnings. A read-only `models status --agent runway-worker --json` under that copy still resolved `openai/gpt-5.6-luna`, one OpenAI OAuth provider, zero missing providers, zero route issues, and zero fallbacks. The temporary config was removed. This is **configuration evidence only**; the Gateway load result appears below, and an actual worker OAuth request through the alternate harness has not been proved.

## Required proof before enabling work

The adapter has passed a network-disabled SSE negative control and is loaded in the business Gateway, but the complete worker request and recovery path is unproved. Keep `RunwayLiveInferenceEnabled` false. Before opening it, prove that the worker uses this exact fetch path for ordinary sends, retry/continuation, and compaction; that the ledger refuses the request and token ceilings before excess dispatch; and that cancellation and host restart leave uncertain sends held. Confirm that the selected OAuth profile remains subscription backed and that no API-key or paid fallback is selected. Then load the new host backend through an ordinary permitted restart, release one owner-reviewed grant with a fresh pilot-wide admission check, and record the actual request and token receipts.

Until that proof exists, the saved revision instruction and ledger's held-grant structure are durable data. The owner-facing grant API deliberately returns 409 so an expiring 30-minute grant is not consumed while release cannot occur.

## September 24 correction: native OAuth bypass and meter v3

The earlier `buildModelFetch` result did **not** cover the actual OAuth worker. A disposable Gateway with a fictional OAuth profile selected OpenClaw 2026.9.4's native `openai-chatgpt-responses` provider. That provider calls process `fetch` directly, outside `buildModelFetch`; with the initial adapter it attempted DNS with no ledger reservation. The container had `--network none`, so no request left. Meter v2 was then made explicitly unready and blocked worker turns until this route could be guarded.

Meter v3 wraps both the managed Responses fetch seam and process `fetch`, and pins readiness to OpenClaw `2026.9.4`, the exact SSE worker model, conversation-hook access, and both installed guards. It accepts the native provider's full internal session ID or the managed transport's clipped header, and checks it against the active durable execution ID. An active execution blocks unrelated process fetch traffic; paid/API-key Responses URLs are refused even without a claim. A status read repairs OpenClaw's post-turn transport replacement before the host preflight. The host now requires version v3, `guardInstalled:true`, and `nativeGuarded:true`.

The v3 negative control used a disposable Gateway with no network, no owner volume, a fake OAuth JWT in its own worker database, and a fake active ledger that logged then denied reservations. The installed runtime selected an OAuth profile with no API key or fallback. Its actual `modelRun:true` worker turn attempted the native ChatGPT Responses send four times; all four reached the fake ledger with the same execution ID and request digest, and each ended `Runway request was not admitted for dispatch` before a network send. Afterward a status read repaired the transport and returned v3 ready. The disposable container was removed. The real business Gateway was rebuilt with v3 and its original `dev_state` volume; the shared Gateway retained `marketing_shared_state`. Both are up, with the live-inference gate still false.

This proves the *denial* path of the native OAuth request and the status repair. It does not yet prove an admitted native response, per-request usage settlement from a successful turn, or interrupted-send recovery in the live host. The real project was not advanced. The old Windows host still owns port 5189, so its backend has not loaded the v3 preflight. Keep the live gate closed until those remaining checks pass.

## September 24 Gateway session and late-init proof

The installed Gateway was exercised in a disposable `--network none` container with a dummy credential and a fixture ledger; it never mounted the owner's `dev_state` volume. With `modelRun:true` and `promptMode:"none"`, OpenClaw 2026.9.4 replaces the supplied worker session with `internal-session-effects-<execution ID>-<SHA-256 prefix of execution ID>` and the corresponding `agent:runway-worker:internal-session-effects:...` key. Its native ChatGPT Responses transport truncates the `session_id` header to 64 code points. The v2 adapter derives both identities from the durable execution ID, checks the full key at `before_agent_run`, and checks the truncated header at every guarded fetch. The original v1 comparison would have blocked a legitimate worker turn.

The first actual Gateway turn showed another late initialization: OpenClaw replaced `buildModelFetch` after Gateway service startup but before `before_agent_run`. The hook denied that turn. The v2 hook now reinstalls the wrapper immediately before allowing an active, exact-session worker. A second network-disabled turn with the fixture claim reached the guarded fetch. The dummy API key intentionally selected `https://api.openai.com/v1/responses` with no ChatGPT session header; the guard rejected that route before calling its base fetch. OpenClaw attempted same-model turn retries, and each reached the hook/guard again without a permitted send. This proves the Gateway's hook and fetch path for that negative control, not OAuth selection or a successful worker reply.

The repeatable installed-package tests cover initial denial, encrypted-content recovery's second request, compact denial, lazy transport setup, an unclaimed worker hook block, and repair after a late host replacement: **6 passed** in a disposable `--network none` container. Four local fetch tests, 34 Python ledger tests, and five focused host tests also pass. The derived image copies only the five production plugin files; the fixture ledger and tests remain outside that image. The preserved business Gateway was recreated with `dev_state` intact and now reports `marketing-meter-v2`, `policyReady:true`, `guardInstalled:true`, and `ready:true`; cron is disabled with no next wake. The historical pilot remains `needs_review`, version 11, with three artifacts, four executions, zero reviews/grants/model-request receipts, 8,618 reported tokens, zero reservations, and no active execution.

The production Gateway has a usable OpenAI OAuth profile in read-only model status, but the alternate JavaScript worker harness has not completed a real subscription request. The old .NET host on port 5189 has not loaded the new metering backend, and `RunwayLiveInferenceEnabled` remains false. No owner grant, real model request, publication, Plow send, or paid fallback was made in this proof.

The guarded fetch also rejects a paid or alternate endpoint when **no** runway claim is active. This closes a configuration-error path in which the same model might otherwise use a direct API key outside the runway. Owner Chat on the subscription Responses URL still passes when no runway owns the transport; its usage remains outside the runway ledger. Four local fetch tests and six installed transport/plugin tests pass after this restriction.

A seventh installed transport test specifically invoked OpenClaw's generic paid Responses stream with no active runway claim. In `--network none` it returned an error before the synthetic base fetch, with **zero sends**. The current installed transport/plugin total is **7 passed**.
