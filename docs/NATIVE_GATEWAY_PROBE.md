# Native Gateway identity and access probe — September 24

This was a **disposable local fixture**, not the running Marketing Gateway and not a two-human demonstration. It used the installed OpenClaw `2026.9.4 (3a9d69d)` binary with a separate `/tmp` state directory and loopback port `18995`. No `chat.send`, `sessions.send`, or initial-message RPC was issued. The production Gateway on `18795`, its `dev_state` volume, and the saved marketing runway were not changed.

The fixture configured identity-bearing `trusted-proxy` authentication for `owner-fixture@local.test` and `collaborator-fixture@local.test`, named roles, a tool-denied `shared-marketing` agent, and a separate tool-denied `main` agent representing private owner sessions. The test client connected over WebSocket protocol 4 with a local synthetic proxy header. This proves the installed protocol behavior under those fixture assertions; it is **not** a production proxy or verified real-world sign-in.

| Probe | Installed Gateway result |
| --- | --- |
| Two asserted fixture identities | The Gateway accepted both with `operator.read` and `operator.write` and stamped different durable profile IDs on sessions they created. |
| Shared session visibility | The collaborator could list the same owner-created `shared-marketing` session. No message was sent, so participant history and reply routing were **NOT RUN**. |
| Agent allowlist | With the collaborator role active, `sessions.create` targeting `main` returned `FORBIDDEN`. |
| Private session read | With `sessions.others="write"` so the collaborator could participate in an owner-created shared session, `sessions.list` exposed the owner-created `main` session and `sessions.describe` returned it successfully. This **fails** the required owner-private boundary. |

The role's agent allowlist controls creation/runs, but does not by itself hide foreign private sessions when `sessions.others="write"`. The [installed operator-scopes contract](https://docs.openclaw.ai/gateway/operator-scopes) also says `operator.write` includes Gateway-wide control-plane actions. Therefore a direct collaborator Control UI/Gateway connection to the current single Gateway cannot be enabled safely merely by adding profiles and roles. The local branded device-session checks are a separate, narrower host API proof.

### Why narrower session roles do not fix this fixture

The installed `2026.9.4` operator-scopes documentation defines `sessions.others="none"` as hiding foreign sessions, `"view"` as read-only, `"suggest"` as a suggestion flow, and `"write"` as participation in foreign sessions. It says explicit session membership can raise **view or suggest** access for one session; it does not grant targeted write access. Thus changing the fixture collaborator to `none`, `view`, or `suggest` would protect the private session but would not meet the requested same-conversation collaboration contract. The broader `write` role demonstrably exposes the private session. A second role-only fixture would exercise a documented denial rather than resolve this boundary. The installed [multi-user contract](https://docs.openclaw.ai/concepts/multi-user) also states that ownership and visibility are usability features, not security boundaries.

This is a limitation of the current **single-Gateway, direct collaborator connection** design. It does not establish that OpenClaw cannot support multiplayer on a separate constrained Gateway or behind a method- and session-filtered authenticated relay. Neither alternative has been implemented or accepted here, so the production collaborator route remains disabled.

Keep the collaborator native route unavailable. A supported identity-aware ingress must be combined with a narrowly method- and session-filtered host relay, or a separate Gateway trust boundary containing only shared material. The host must map the authenticated Gateway actor and exact accepted message ID to the existing `hire.sqlite` input record and retain grant/dispatch authority. Test private-session reads, full-tool agent selection, tool invocation, owner controls, budget changes, duplicate input, membership, and reply destination before allowing real participants. The second person and actual reply remain **NOT RUN**.

For future customer isolation, this local pilot is **one business per host state root and Gateway state volume**. Another customer needs separate employee state, model credentials, and ledger; a second profile or role in this Gateway is insufficient. Members of one business may eventually share only its constrained conversation and approved project material. The fixture above specifically falsified treating named roles alone as a private-session boundary.

The disposable Gateway exited cleanly and port `18995` closed. Its container-local `/tmp/marketing-native-probe` directory was removed after checking the resolved path. Automatic approval review rejected deletion of the separate host fixture directory `artifacts/native-identity-probe`; it remains ignored by Git. No alternate deletion route was used.

## September 24 continuation: native suggestion and isolated Gateway

A second **disposable, no-model fixture** checked `session.suggestions.add` on the same installed `2026.9.4` package. Under `sessions.others="suggest"`, an authenticated collaborator could add one pending suggestion to an owner-created `suggest` session; the receipt carried a distinct Gateway profile ID. The same role could also list and read an owner-private session, so it **did not** repair the direct-connection boundary. With `sessions.others="none"`, the private session was hidden, but the collaborator could not see or suggest into the shared session even after explicit membership. Neither variant sent a model message. The temporary Gateway was stopped and its verified container-local state was removed.

The local implementation now has an **optional isolated shared Gateway** in `business/agent/compose.shared.yml`. It uses the pinned `marketing-hire:dev` image, a separate `marketing_shared_state` volume, one tool-denied `shared-marketing` agent, an exact two-identity allowlist, no published port, disabled cron/dreaming/heartbeat, and a small host-only RPC adapter. The owner Gateway, OAuth store, and `dev_state` volume are not mounted into it. The host source adds a project-to-native-session mapping, an owner-approved collaborator-device binding, a verified suggestion receipt, and an idempotent ledger input derived from the Gateway suggestion ID. Uncertain receipts remain unknown and are not resent. The adapter deliberately has no model-send or suggestion-accept action while the live budget gate is closed.

The sidecar started and a **synthetic** owner profile created a session; a **synthetic** collaborator profile submitted one pending suggestion with a different profile ID. That fixture session was renamed `fixture-retired-…` and made draft; the collaborator then received `unknown session` on a targeted read. No fixture suggestion was imported into the owner's real runway. This proves local protocol and container separation, not real two-human participation or a completed reply. The cockpit asserts a Gateway identity only after authenticating its own owner or owner-approved paired device. It requires an observed non-loopback client address for the trusted-proxy request; IP address alone is not treated as human identity. The running host at `5189` still uses the prior binary because automatic approval review rejected the stop/restart command; the new API awaits an ordinary host restart.

A read-only adapter probe with forwarded `127.0.0.1` returned HTTP 403. The installed Gateway logged `unattributable proxy-shaped traffic` for that connection, so the temporary localhost allowance in the relay was reverted. Do not assert a different forwarded client address to work around this check. The remaining local ingress requirement is a genuinely observed non-loopback client connection through an authenticated, narrowly trusted host route.

After the relay was staged, two no-model negative controls used the isolated sidecar's host-only adapter. An unsupported `chat.send` action returned `Shared Gateway action is unavailable`; a `suggest` request targeting `agent:main:private` was rejected before a Gateway connection with `Exact shared Marketing session required`. These are adapter checks, not browser-origin security or real-user acceptance. The adapter has no send/resolve action, and the sidecar still has no published port.
