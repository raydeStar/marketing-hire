### Narrower runtime envelope and the live gate

The local code can admit at most six **opaque Gateway turns** for one assignment, reserve 25,000 ledger tokens per claim against a 150,000-token allowance, stop after 15 minutes of recorded active execution or a 30-minute assignment deadline, allow two structural repair attempts per step, and request at most 1,800 output tokens per worker turn. It records aggregate usage after a turn settles and charges conservatively if usage is missing. The worker has no tools, scheduled heartbeat, or fallback model. These are useful admission and recovery controls, but they do **not** enforce the requested ceiling of 20 underlying provider requests or 250,000 actual input-plus-output tokens: the installed Codex app-server route is an opaque turn in OpenClaw's own telemetry, and retries inside it are not individually admitted by this host. The runtime's `llm_input` and `llm_output` hooks are adapter observations, not request preflight. New autonomous inference remains hard-disabled in source; no environment switch can waive that gate. Owner-initiated direct Chat is outside this assignment ledger and must be treated separately when judging total usage.

## Native conversation integration boundary

The installed [multi-user contract](https://docs.openclaw.ai/concepts/multi-user) records creator and participants only when an authenticated Gateway profile or channel sender supplies identity. A shared token does not distinguish humans. The installed [Gateway integration contract](https://docs.openclaw.ai/gateway/external-apps) recommends WebSocket RPC/events and `sessions.*` for external apps. Its `gateway.roles` policy can restrict authenticated profiles to specified agents and session access, but the current Gateway has no identity-bearing local reverse proxy or Tailscale identity and no collaborator role. OpenClaw also documents that operator write scope includes Gateway-wide actions and that same-agent ownership is not isolation.

The [disposable native probe](NATIVE_GATEWAY_PROBE.md) confirmed that a role allowlist rejects creating a `main` session but does not conceal an existing private `main` session under the `sessions.others="write"` policy needed for the shared owner-created session. The host authenticates a device, maps a verified Gateway suggestion profile/session/ID to an idempotent project input, and retains grant/dispatch authority. The direct collaborator route to the original Gateway remains unavailable. A second real person must join the **same** session and receive a reply before multiplayer acceptance can be called complete. No new external channel, tunnel, or deployment was enabled here.

Installed `2026.9.4` session roles leave no safe direct-connection setting for the original single Gateway: `none` hides foreign sessions by default, `view` cannot mutate them, and `suggest` allows only suggestions. Explicit membership can elevate only view/suggest for one session. `write` permits collaboration but the fixture proved that it also reveals owner-private sessions. The staged separate Gateway/relay still needs a loaded host binary, a second authenticated human, an actual reply route, and a verifiable provider-request accounting contract for a new live revision demonstration.
