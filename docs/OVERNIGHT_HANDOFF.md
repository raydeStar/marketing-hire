## Native conversation integration boundary

The installed [multi-user contract](https://docs.openclaw.ai/concepts/multi-user) records creator and participants only when an authenticated Gateway profile or channel sender supplies identity. A shared token does not distinguish humans. The installed [Gateway integration contract](https://docs.openclaw.ai/gateway/external-apps) recommends WebSocket RPC/events and `sessions.*` for external apps. Its `gateway.roles` policy can restrict authenticated profiles to specified agents and session access, but the current Gateway has no identity-bearing local reverse proxy or Tailscale identity and no collaborator role. OpenClaw also documents that operator write scope includes Gateway-wide actions and that same-agent ownership is not isolation.

The [disposable native probe](NATIVE_GATEWAY_PROBE.md) confirmed that a role allowlist rejects creating a `main` session but does not conceal an existing private `main` session under the `sessions.others="write"` policy needed for the shared owner-created session. The next supported connection needs an identity-aware ingress that cannot be bypassed **and** either a method/session-filtered host relay or a separate Gateway trust boundary containing only shared material. Gateway must supply authenticated sender/session/message IDs to the host; the host should validate membership, deduplicate the message ID, then record a project input in `hire.sqlite`. The host remains the only grant/dispatch authority. Verify direct RPC and agent-mediated attempts to change budget, approve, pause, or read owner-only material against protected state. Keep the native path unavailable until those checks pass. A second real person must join the **same** session and receive a reply before multiplayer acceptance can be called complete. No new external channel, tunnel, or deployment was enabled here.

Installed `2026.9.4` session roles leave no safe direct-connection setting for this single Gateway: `none` hides foreign sessions by default, `view` cannot mutate them, and `suggest` allows only suggestions. Explicit membership can elevate only view/suggest for one session. `write` permits collaboration but the fixture proved that it also reveals owner-private sessions. The exact next implementation decision is whether to put the shared employee in a **separate constrained Gateway** or build a **method- and session-filtered authenticated relay**; either must be proved against private reads and owner-control bypasses before a collaborator is admitted. A second authenticated human and a verifiable provider-request accounting contract are then needed for the morning revision demonstration. The historical three-artifact pilot remains available for review meanwhile.
